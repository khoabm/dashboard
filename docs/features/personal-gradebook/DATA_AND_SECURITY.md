# Data and security design — Bảng điểm cá nhân

**Status:** preferred technical design for BRIEF V1.1 (2026-10-26); no schema/API deployed. Business decisions live in [BRIEF](BRIEF.md); technical defaults below require CP01 verification. Read [existing DATABASE](../../DATABASE.md), [SECURITY](../../SECURITY.md), and current Supabase docs before implementing. The current application's six `public` tables (`boards`, `sections`, `posts`, `attachments`, `admin_profiles`, `audit_logs`) retain their existing board semantics/client policies; §I proposes additive server-written Gradebook audit events only.

Implementation-ready refinement and observed environment evidence: [CP01-A technical design](CP01_TECHNICAL_DESIGN.md). This overview keeps the high-level contract; that design specifies column details, RPC/Edge DTOs, locks, key lifecycle and test matrix without changing BRIEF.

## A. Minimal extensible data model (six small tables)

Avoid 8×7 columns, separate semester tables, multiple score tables per subject, generic EAV metadata or a full permissions framework. Use one row per recorded score and **two small seeded catalogs** for future extensibility. Example shape; actual SQL migration must be reviewed before any apply.

| Table | Minimum columns and constraints | Purpose |
| --- | --- | --- |
| `classes` | `id UUID PK` generated; `name TEXT NOT NULL`; `school_year TEXT NOT NULL`; `is_active BOOLEAN NOT NULL`; `semester_1_published_at TIMESTAMPTZ NULL`; `semester_2_published_at TIMESTAMPTZ NULL`; timestamps; partial unique active class | One active class; name/year editable metadata, no historical label snapshot |
| `students` | `id BIGINT GENERATED ALWAYS AS IDENTITY PK`; `class_id FK`; `full_name TEXT NULL`; `birth_date DATE NOT NULL`; `identity_ciphertext BYTEA NOT NULL` + nonce/key/algorithm version; `identity_lookup BYTEA NOT NULL` (32 bytes); `active BOOLEAN`; timestamps; `UNIQUE(class_id,identity_lookup)` | Teacher CRUD with two mandatory identification fields, DB-generated internal ID; detailed revision/capability fields in CP01-A |
| `subjects` | `code TEXT PK`, `display_name TEXT`, `sort_order SMALLINT UNIQUE`, `active BOOLEAN` | One central ordered subject vocabulary, V1 seeded with exactly eight names from BRIEF |
| `score_columns` | `code TEXT PK`, `display_name TEXT`, `sort_order SMALLINT UNIQUE`, `active BOOLEAN` | One central ordered score vocabulary, V1 seeded with exactly seven names from BRIEF |
| `student_scores` | `student_id BIGINT FK`, `semester SMALLINT CHECK IN (1,2)`, `subject_code TEXT FK`, `score_column_code TEXT FK`, `score NUMERIC NOT NULL` with 0–10 and five-fractional-digit validation, `created_at`, `updated_at`, `updated_by UUID FK to auth.users`; composite PK of (student, semester, subject, score column) | Exact validated decimals; 0 != no row; atomic UPSERT import |
| `lookup_attempts` | Scope (global/document), fixed-window key/start, HMAC document key where applicable, counter, expiry index; unique scope/key/window | Atomic throttle and bounded cleanup in this same table; no raw identity, DOB or IP |

`classes.id` uses the existing UUID convention and anchors audit events (§I). `students.id` is **auto-increment** and crosses API boundaries as a string, never a required import field. Generate stable catalog codes, never UI labels; seed exact GB-04/05 names/orders and render from catalogs rather than scattered JS/SQL copies.

All student queries derive class from the owning record; never accept a client-chosen student ID as read authorization. Updating `classes.name` or `classes.school_year` updates metadata only: do not touch students, scores, publication state or IDs, and do not create a class. The old year label is not independently preserved. No automatic rollover, student copying or history table. Restrict class delete when students exist; default student removal to deactivation, preserve points and require explicit reviewed deletion semantics. Audit follows §I.

**Decimal contract (GB-06 / user D01):** score fields in API requests/responses are decimal strings. Validate a finite nonnegative ordinary decimal with at most five fractional digits and value 0–10 before conversion/storage. Technical grammar: ASCII digits with optional dot and 1–5 fractional digits; reject exponent, sign, NaN/Infinity and ambiguous separators rather than guessing. Never route authoritative writes through JavaScript Number or `toFixed`. Use scale-free PostgreSQL `NUMERIC`, with range and fractional-precision validation in the transactional entrypoint and a defensive constraint; reject, do not round/cast into validity. Validation examines the input representation before normalization, so `8.123456` is invalid even if later formatting could hide digits. Insignificant trailing zeros need not survive (e.g. `10.00000` and `10` represent the same value).

Form/CSV preserve lexical decimal strings. Excel text cells follow the same rule; the chosen parser must expose a decimal representation suitable for validation for numeric cells, rejecting unrepresentable/ambiguous values rather than rounding them to five places. Do not claim recovery of digits Excel already lost. All numeric-cell conversion choices need CP03/04 fixtures, including a sixth decimal and boundary values. Sort/compare/calculate using raw decimal semantics (DB NUMERIC or exact decimal/string/scaled-integer logic), never lexicographic string order. Conversion of a bounded bucket coordinate for drawing is presentation only. Technical display/grouping default: decimal half-up for nonnegative values to one place, pending CP01/06 verification; `8.24 → 8.2`, `8.25 → 8.3`, `8.26 → 8.3`. The student's raw score remains a separate decimal string.

Required round-trip/regression: `8`, `8.1`, `8.12345`, `8.24`, `8.25`, `8.26`, `0`, `10`, `10.00000`; reject `8.123456`, `10.00001`, `-1`, non-decimals and out-of-range values at form/parser/API/DB boundaries. Test INSERT and UPDATE, unchanged numeric equality despite trailing zeros, raw sorting and histogram bucket matching.

## B. Scope and migration safety

- Preferred isolation: put the six new tables in a non-exposed `gradebook` schema. Revoke object/schema/sequence access from PUBLIC, anon and authenticated; enable RLS with no client policies as defense in depth. Grant only required privileges to the server role for §E entrypoints. Verify effective/default grants in CP01; do not add this schema to exposed schemas.
- Existing `public` board tables/RLS and existing single-admin `admin_profiles` are untouched. No Supabase Auth accounts per student.
- Write an **additive versioned migration**, transactionally applied after schema/security review on an approved environment, with indexes, grants, FK restrictions, constraints and idempotent catalog seed. Confirm no collision with preexisting private schema/routines.
- Migration/rollback notes must explain how to restore without deleting grades or touching board data. Do not apply to live project in a docs-only pass; never add real PII to seed/test.
- Preserve one active class invariant. School year is editable metadata with the GB-01 trade-off; no history/rollover or multi-class UI.
- When catalog names/order change in a future version, use a dedicated migration and preserve existing score FK codes.

## C. Identity handling and lookup

1. Teacher entry / file import: validate 9–12 ASCII digits and real date, preserve leading zeros. HTTPS transport only. **Never treat CMND/CCCD as DB PK or a numeric column.**
2. A server-only Supabase Edge Function computes an HMAC-SHA256 **blind index** (private pepper) for exact matching and uniqueness; encrypts original document number with an authenticated reversible cipher (AES-GCM, random nonce per record). Store nonce/algorithm version with ciphertext, never in plaintext fields. **Separate keys** for HMAC and encryption, provisioned through function secrets. Re-key rotation must be possible without losing IDs.
3. Admin may decrypt only in an explicitly authorized workflow (prefer masked display; do not return entire cleartext identifier lists by default).
4. Student supplies document number + date via a **POST body** to a server-controlled lookup; server computes HMAC and checks date + active student + publication. Generic denial must not disclose which part matched. Neither inputs nor raw identifiers may be logged/placed in URLs, analytics, service traces, client persistent storage, backups in Git or test artifacts.
5. Lookup issues a short-lived **memory-only** opaque or signed capability limited to one student (and current class), validated server-side for each subsequent grade/histogram read; never use a client-supplied student id to choose records. Expiry and unpublish/deactivation revoke access on each server-side read.
6. This is **knowledge-based identity verification, not strong authentication**. Anyone who knows the pair may impersonate the student. No OTP/student Auth is added. Fail closed on authorization/publication/throttle failure; deferred statistical suppression (§D) is not an access prerequisite.

## D. Rate-limit and privacy design

- **Approved behavior:** server-side, atomic per-document and cross-document throttling; no frontend-only debounce, per-instance memory, trusted arbitrary IP header or paid service. Preferred V1 uses document HMAC + global endpoint budgets in the same `lookup_attempts` table, so changing IDs cannot reset all counters and no IP trust is required.

| Technical defaults pending verification (not user-approved thresholds) | Proposed limit |
| --- | --- |
| Pair-verification attempts for the same document HMAC | 5 per fixed 15-minute server-time window |
| All pair-verification attempts across identities | 60 per fixed minute AND 300 per fixed 15-minute window |
| Capability-authenticated grade/histogram reads, separate global scope | 120 per fixed minute; no eager 56-chart fetch |
| Window retention/cleanup | Expire at window end + 30 minutes; delete up to 500 expired rows per limiter transaction, indexed by expiry |
| Memory-only student capability lifetime | 10 minutes; recheck active student/class and publication on every read |

- Charge global verification budgets for successful, failed, unknown and malformed attempts. Check/increment global rows before allocating a per-document row; invalid identity syntax consumes only global budget. Serialize rows in deterministic order using DB atomic updates/locks and server time; return an allowed/denied result, **commit denied-attempt counters**, then form the neutral HTTP response (do not raise an exception that rolls counters back). Window boundary bursts are a known fixed-window trade-off; test them explicitly. Cleanup runs with traffic, no separate cron/service; idle expired rows may remain until the next cleanup. Verify bounded allocation and cleanup backlog under rejected/random-identity traffic in CP01.
- Budget exhaustion: generic rate-limited response (e.g. 429); limiter DB error/timeout/unverifiable state: generic unavailable response (e.g. 503), **no identity lookup or grade response**. Neither body reveals existence or which credential matched. Reads with invalid/expired capability reveal no data either. Availability on shared school networks and denial-of-service remain risks to measure; this is not a WAF or a guarantee against distributed attacks. Tune defaults only with dated evidence and recorded rationale, not a new paid dependency.
- Return no PII when credential mismatch/expired/blocked. No direct anon table reads. Teachers write only after verifying live Supabase Auth user and `active admin_profiles` via server; never trust `user_metadata` or frontend flags. An Edge Function using a privileged secret key bypasses RLS, so enforce authorization and specific payload validation on every operation.
- Restrict CORS origins as practical for deployed site and controlled QA; CORS is not authorization. No secrets/PII in static Vite bundle. `Content-Security-Policy`, safe text rendering, no persistent credential cache, response `Cache-Control: no-store` for private grade APIs.
- Histograms return only `{score_bucket, student_count}` aggregates for the selected published semester + subject + column in the active class; no peer names, document numbers, DOB or raw scores. Own raw score is separate. **Statistical inference is Accepted / Deferred for V1**: no cohort threshold, minority-bucket suppression, privacy engine or additional table/logic. This is not a CP05 blocker and does not mean inference risk was eliminated. Revisit in a separate milestone. Verified access, no direct client table access and publication checks on every request remain mandatory, including old capabilities after unpublish.
- Distinguish chart **bucket** from raw score. Group by display tenth via a deterministic decimal half-up rule. Highlight the matching bucket and show exact personal raw score separately; do not falsely claim grouped students have identical scores. On an unavailable score, show neutral empty state/no highlight.
- Audit high-impact admin actions (import, delete, publish/unpublish) without writing raw identifiers or full row payloads. Determine legally appropriate retention and backup controls for children's information before real data import.

## E. Minimal Edge API contract

Two functions (no standalone server), separated responsibilities:

| Function | Allowed caller | Operations |
| --- | --- | --- |
| `grades-admin` | Existing authenticated verified active admin only | class metadata; student CRUD/secure reveal when necessary; roster UPSERT; manual score CRUD; score UPSERT; semester publish/unpublish |
| `student-lookup` | Anonymous user with pair verification or valid short-lived lookup capability | verify pair and return limited own published grades; one selected aggregate histogram when requested |

Callers' Supabase `publishable` key does not confer admin rights. Authenticate `grades-admin` using verified JWT/user/profile **before privileged DB access**, including import and reveal. Differentiate invalid/expired/revoked user. For public lookup, use narrowly scoped endpoint; if platform's function-level JWT verification is disabled for access by anonymous students, this does **not** bypass application-level validation, server throttling or grade publication checks. Keep privileged secret confined to server environment.

**Preferred transaction bridge (GB-REV-006):** Edge calls narrowly named `public.gb_*` RPCs via its server-role client, because `public` is already exposed while `gradebook` tables are not. These RPCs are `SECURITY INVOKER`, use qualified object names/fixed search_path, and explicitly REVOKE EXECUTE from PUBLIC, anon and authenticated; GRANT EXECUTE only to service_role, with the minimum required schema/table/sequence grants. No direct browser invocation, new exposed schema, generic SQL/transaction executor or change to existing board RPCs/private helpers. Confirm anon/authenticated/non-admin direct RPC calls are denied, not merely hidden by UI. Sources: [database functions](https://supabase.com/docs/guides/database/functions), [API grants](https://supabase.com/docs/guides/api/securing-your-api).

**Atomic UPSERT:** one file → one bounded RPC transaction. Edge revalidates untrusted input and computes secure identity material; RPC rechecks row constraints, identity/DOB matching, active class, active student for score import, allowed update fields, admin and publication under locks. Roster can update an inactive student's allowed name field without reactivating them. Lock class before import/publication and resolve/write students/slots consistently; use unique constraints/UPSERT conflict targets to prevent duplicate rows. Recompute INSERT/UPDATE/unchanged/error outcomes against current DB state, not client preview counts. Any error or race conflict aborts **all mutations**; successful batch commits rows + §I audit together. Existing slots are legitimate UPDATE targets, not errors. Preferred concurrency safeguard: compare affected records with expected prior values from the authorized preview under the same transaction locks. A changed preview returns a stale-preview response with zero writes and requires refreshed preview/confirmation. It grants no additional permission and needs no persistent preview file/new table. Same-value retry is unchanged, not duplicated; no last-write-wins for duplicates within a file.

For privileged requests, verified teacher UUID is server context, never accepted from an untrusted actor field. RPC checks that UUID is still an active admin under the transaction's authorization check; it must not infer teacher identity from the service-role token. Parameter validation/operation allowlists remain mandatory despite RLS bypass. Import of scores remains forbidden while the selected semester is published; publish/unpublish and import use a common lock so preview-time checks cannot race. Metadata-only year/name updates have no score/student/publication side effects. Partial frontend batch requests are not an alternative to this bridge.

CP01-A inspection found service_role lacks auth.sessions SELECT. Revoked-session enforcement therefore uses the [narrow non-exposed read-only helper](CP01_TECHNICAL_DESIGN.md#51-common-rules-and-teacher-authorization) proposed in the design, after JWT verification; public gb_* RPCs remain SECURITY INVOKER. This does not grant broad Auth-table access or alter the board's private.is_admin helper.

## F. Excel/CSV contract and controls

**Students — accepted header layouts in both CSV and XLSX:** `CMND/CCCD`, `Ngày sinh` (minimum valid two-column file), **or** `Họ tên`, `CMND/CCCD`, `Ngày sinh` (three-column file). The `Họ tên` header itself may be **absent**, not merely present with blank values. If absent or blank, leave the stored name unchanged during UPSERT; new students may have a NULL name. Do not require or synthesize a student ID/import key. The optional header, when present, precedes the two required headers.

**Scores — ordered visible headers:** `CMND/CCCD`, `Ngày sinh`, `Môn`, `Thường xuyên 1`, `Thường xuyên 2`, `Thường xuyên 3`, `Thường xuyên 4`, `1 tiết`, `Giữa kì`, `Cuối kì`. Semester chosen in teacher UI before upload. `Môn` cell matches one of eight literal GB-04 labels. No teacher-entered ID/key. Prevent PII-bearing imports from being uploaded to Storage or included in repository artifacts.

Validate file type/size/row cap/encoding, headers, identities/dates, §A decimal contract, student existence for score import and class/semester permission. Technical safety defaults (pending CP03/04 parser/runtime verification): file ≤1 MiB, ≤2,000 data rows; reject excessive decompressed XLSX size/complexity, formulas and ambiguous cells with clear correction guidance before writes. Choose/pin a small maintained parser only when implementation is authorized. Excel identifiers must be text, not reconstructed with guessed zeros; dates require explicit DD/MM/YYYY/text and Excel date-system/timezone/leap-day tests. No promise to recover numeric precision or zeros already lost by Excel. Protect generated spreadsheets/CSV against formula injection.

**Roster matching:** lookup key is `(class_id, identity_lookup)` and DOB must match for UPDATE. New identity inserts with DB-generated ID; existing matching identity updates only allowed name field. The parser must accept both the exact two-header and three-header layouts above; an absent `Họ tên` column is not a malformed header. **Minimal technical allowlist proposal:** nonblank imported name may change `full_name`; blank/missing name preserves old value; import never changes DOB/document number/class/active status or silently reactivates a student. Manual authorized CRUD handles those changes. Duplicate roster identities inside one file are errors even if equal; mismatch DOB is a conflict. These details operationalize GB-07 and remain technical choices to verify, not extra user-approved business scope.

**Score matching:** resolve existing active student by document + DOB, then UPSERT on `(student_id, semester, subject_code, score_column_code)`. Missing coordinate INSERTs; different valid numeric value UPDATEs; equal numeric value is unchanged, including insignificant trailing-zero differences. Blank cells are counted as skipped and never clear/write 0. Same student in different subjects is valid. Reject repeated nonblank score coordinates anywhere in the file even if values match; no last-write-wins. Conflicting identity/DOB, invalid cells or duplicate coordinates block the whole file.

Preview/result counts explicitly separate INSERT, UPDATE, unchanged and error, plus skipped blanks; roster unit is a student, score unit is a nonblank coordinate. Row/column errors are admin-only ephemeral UI, never raw logs. Server recomputes and confirms a stale preview per §E before any commit. An error causes zero mutations across both new and existing rows, including audit; rollback must preserve previous values. Raw files never go to Storage/persistent caches/Git.

**Data transaction outcomes:** success applies all validated INSERT/UPDATE changes or failure applies none. No partial-success UI. A lost-response retry revalidates current data; same raw values become unchanged, while intervening manual changes require refreshed preview/confirmation. Do not promise blanket idempotence that could overwrite newer edits.

- CP01 verifies §D technical limiter/capability defaults, transaction bridge and key lifecycle; CP03/04 verify bounded parser and UPSERT semantics. Suppression is deferred, not an unresolved V1 gate. Manual edits to a published semester retain the GB-06 warning and affect subsequent reads immediately.

- Decide how new client routes share existing admin state without forcing student login; confirm host deep-link fallback and CSP for Supabase Functions, not Cloudflare Quick Tunnel's ephemeral host.
- Backup/restore plan must include encryption keys in a controlled secret-backup procedure; losing keys loses access to reversible identifiers. Do not store them in Git.

## H. Real personal data gate

**NOT RUN; required before any real student entry/import, not just before CP07/deploy.** Synthetic development/tests can proceed earlier. An accountable owner must record: authorized purpose/right to process; allowed fields and access; retention and explicit deletion procedure; encryption/HMAC key custody/versioning/rotation; authorized encrypted backup location and successful synthetic recovery of data + keys; actual server authorization and deny tests; log/trace/error redaction checks. Record environment, date, reviewer, evidence and unresolved blockers in checkpoint reports without PII/secrets. Missing approval/evidence blocks real data, not synthetic development. Key loss prevents decrypting IDs; HMAC key loss/rotation can break lookup/uniqueness, so both keys need controlled recovery. Do not use this document to claim legal compliance or authorization already exists.

## I. Minimal audit proposal (GB-REV-007)

Existing `public.audit_logs` uses a UUID target and `private.audit()` assumes a row `id` plus caller `auth.uid()`; students use BIGINT and scores a composite key. **Do not attach that trigger to Gradebook.** Preferred minimum: reuse the audit table with the owning `classes.id` UUID as target. RPC supplies verified teacher UUID as actor (§E) and an allowlisted Gradebook action, with optional aggregate INSERT/UPDATE/unchanged counts encoded in the action. Audit roster/score UPSERT batches, student delete/deactivation, manual score edit/delete and semester publish/unpublish; no document number, DOB, names, student IDs or personal score payload in logs. Class metadata edits can use the same class-level action pattern.

Write one class-scoped audit event in the same mutation transaction, server-side only; unchanged-only imports may record aggregate completion but do not rewrite score rows/timestamps. Browser roles retain no audit INSERT/UPDATE/DELETE grant. Verify the server role's existing audit INSERT privileges in CP01, add only the exact missing server grant if needed; preserve existing board rows, columns, triggers and client policies. No seventh table or UUID encoding of BIGINT/composite IDs. **Trade-off:** this is actor/action/class traceability, not per-student old/new-value reconstruction. Confirm this limitation in CP01 review rather than silently adding detailed PII history.

Do not silently interpret these *proposed* details as additional user-approved features. Implement the smallest secure variant and report tradeoffs. Real data import, auth config changes, DB migration and public deploy remain separate approval/review gates.
