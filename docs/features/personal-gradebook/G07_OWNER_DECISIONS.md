## Operating procedure

1. Before a backup, record approval, snapshot time, original project/AAD identity, source SHA, PG/tool versions, applied ledger mapping and all required row/class/key generations. Inventory all four rings, including active/retained kids needed by every retained snapshot; include expected counts and source/migration checksums. Authenticate binary provenance and available free capacity/egress budget.
2. Coordinate writes and rotations so DB snapshot and key export are consistent. Prefer a short approved maintenance window; never combine an old dump with a newly pruned keyring. A database dump preserves only its DB snapshot, not atomicity with external secrets/Storage. Freeze rotation until both encrypted files and receipts are verified.
3. Preserve schema/data/functions/owners/ACL/default privileges/RLS and application revision/epoch/catalog metadata. Separately plan cluster roles, managed-platform grants, Auth mapping, Edge configuration and Storage bytes. Do not copy live sessions or role passwords as a shortcut.
4. On a separately authorized trusted recovery environment, encrypt the complete custom dump and separate key export to the two approved recipients. Keep raw material in restricted transient staging only. The current scripts remain synthetic-only and must not be used as production exporters. No real data/keyring belongs in Actions.
5. Record a trusted receipt with opaque snapshot ID/time, ciphertext SHA-256/size, version and copy locations. Hashes require trusted custody; hashes stored beside a maliciously substituted pair do not prove provenance. Full age authentication and the inner dump binding precede any SQL execution. Transfer ciphertext only to approved primary/offline locations; recover and compare once under a bounded explicit transfer budget before accepting a copy.
6. Retain last verified copies until both replacements and checks are accepted. Keep no private age identity alongside either ciphertext pair. Preserve historical application keys until all dependent rows and retained backups no longer need them. HMAC-generation migration is a separately authorized locked maintenance procedure, not an automatic rotation performed by this tool.
7. For lost recovery credentials, try the explicitly approved independent/emergency custody route. Without an applicable identity, the ciphertext may be unrecoverable; DPAPI, a public recipient or a new random key cannot replace it. For compromise, contain access and authorize rotation/re-encryption; do not blindly destroy shared historical keys.
8. For a disaster, the incident lead authorizes isolated restoration and trusted backup selection. Verify receipts, project/migration/key mapping and both fully authenticated files before SQL. Create a fresh destination, restore with stop-on-error and a transaction; never reset/overwrite a live project to rehearse. Failure leaves access closed; investigate without blind retries.
9. Verify row/catalog counts, decimal/date values, identity decrypt/HMAC matching, required retained/active keys, capability/preview expiry, owners/ACL/defaults/RLS and actual role denies. Global roles and identity mapping must be provisioned/reviewed separately for a different cluster. New project AAD requires explicit re-encryption design; renaming environment configuration is insufficient.
10. Reapply approved deletions/restrictions since the snapshot before reopening access. Record achieved recovery duration/loss interval, safe evidence and independent review. Institution/owner approve cutover separately. Clear staging, renew encrypted copies, expire obsolete versions/trash/media according to policy and review incident lessons.
