## A2 — Projection boundary

`verificationPayload` requires only the actual B4 success fields plus UUIDv4 requestId; rejects unknown/non-data/getter fields through B1 allowFields. It validates one captured clock, future expiry≤600s, bounded opaque printable capability, public class booleans and complete active V1 ordered catalogs. It returns a detached `{kind:'verified',capability,expiresAt,context}` for the existing memory-only state owner. The capability is **not** a UI DTO and must never be spread into DOM/snapshots/logs/storage. Helpers do not claim to verify GCM/JWT/server identity.

`studentReadPayload` accepts only grades/histogram selection fields, strips only approved requestId, reuses exact decimal and aggregate validators, and rejects peer/private fields and mismatched scope. It does not authorize from a stale publication flag: B3 must decide every read (including republish with an otherwise-valid capability). Invalid projection throws a generic contract category without echoing input; a future authorized transport must map it to safe unavailable. Generic statuses do not substitute for handling a parsed structured422 admin preview.

Helpers have no fetch/SDK/Request/Response/storage or diagnostic logging. The application and production service modules do **not** import them yet. Existing verifyStudent/readStudent/requestGradebookAdmin/loadTeacherCatalog remain byte-unchanged and fail closed locally. The development fixture alone exercises B4-shaped decoded bodies through these helpers. This is useful integration preparation, not a placeholder backend or a claim that production lookup works.
